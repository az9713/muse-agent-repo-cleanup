The short version

Nothing was “hacking” your repository. A scheduled automated check found known security problems in some downloaded development tools. The check was deliberately configured to fail when a high-severity problem appeared. Because it ran every six hours, each failure could generate another GitHub notification email.

4×Scheduled runs per day
5Vulnerabilities reported: 1 moderate, 4 high
74Failures among the last 75 runs checked; the other run was cancelled
The important distinction: an audit warning means a package version matches a published vulnerability advisory. It does not, by itself, mean anyone exploited the repository or accessed your account.

What a security scan actually is

Modern projects rarely contain only code written by the repository owner. They also install reusable packages written by others. The packages may install still more packages. That nested family is the dependency tree.

1Schedule firesGitHub Actions starts “Supply-Chain Watch” on GitHub’s computer.
2Dependencies installThe lockfile tells npm the exact package versions to fetch.
3Signatures verifynpm checks that downloaded packages carry expected registry signatures.
4Advisories comparenpm compares installed versions with its vulnerability database.
5Pass or failA high-severity match makes the job return a failure result.

GitHub Actions

The automation service. A workflow file in the repository describes when to run and which commands to execute. Here, the schedule was 17 */6 * * *: minute 17, every six hours.

npm audit

The dependency checker. It sends the package tree to the configured registry and receives known-vulnerability findings and remediation guidance.

package-lock.json

The exact shopping list. It records precise versions and integrity hashes so automated machines install the same dependency tree repeatedly.

The two commands that mattered

npm audit signatures
npm audit --audit-level=high

The first command passed: 214 packages were verified, including 18 with attestations. The second command failed. The option --audit-level=high means “treat high or critical findings as a failed command.” In automation, a failed command normally stops the job and marks the workflow red.

What happened in ECC-tutorial

We inspected the logs for Supply-Chain Watch run #425. The failed step was called “Verify registry signatures and advisories.” The signature check was healthy; the vulnerability audit was the blocker.

The exact chain from scan to email

  1. The scheduled workflow started automatically.
  2. npm audit found vulnerable versions in the dependency tree.
  3. The audit returned exit code 1, the conventional “failure” signal.
  4. GitHub marked the job and workflow run as failed.
  5. Your GitHub notification settings included CI workflow failures, so GitHub sent an email.
  6. Six hours later, the unchanged lockfile produced the same result again.
Why the email volume was so high: this was not five separate attacks and not five separate GitHub issues. It was one scheduled job repeatedly rediscovering the same unresolved package versions, up to four times a day for roughly three weeks.

A later “Upload IOC report” step also warned that no report file existed. That was a downstream symptom: the audit had already stopped the earlier part of the workflow, so report generation never got the chance to finish.

What we changed

The safest repair was not to silence the scanner. We updated the exact vulnerable versions recorded in package-lock.json to patched versions already allowed by the project’s dependency rules.

These are transitive development dependencies: tools brought in by other tools for linting, testing, or build work. The tutorial’s own source code did not directly import them. That lowers the likelihood that a tutorial reader was directly exposed, but updating them was still the right choice because CI installs and executes the dependency tree.

Changed

Only package-lock.json: 60 lines added, 34 removed. Patched package records included versions, registry locations, integrity hashes, and updated package metadata.

Not changed

No tutorial source code, workflow schedule, notification setting, or security threshold. We did not “fix” the problem by weakening the alarm.

Correction made

An early reading said two packages had no fix. Current patched releases were later confirmed within the allowed version ranges, so all five findings could be resolved without an exception.

What pull request #26 was for

A pull request is a review envelope around a proposed change. PR #26, “Patch vulnerable dependencies to fix Supply-Chain Watch audit failures,” showed the difference between a temporary repair branch and main. It contained one commit and one changed file.

After review, the PR was merged into main using a normal merge commit. The temporary branch was then deleted because its work had been incorporated. The required CI/Lint check passed. A separate “Validate Components” check still flagged pre-existing emoji in documentation/demo files; it was unrelated to this lockfile-only change. Those emoji later became the third failure in the CI episode below — see The CI repair.

The Git lesson hidden inside the repair

Git and GitHub are related, but they are not the same thing. Git is the version-history system. GitHub hosts the repository and adds a website, collaboration tools, automation, and notifications.

1Main branchThe trusted current version of the project.
2Fix branchA safe lane named fix/supply-chain-audit-deps.
3CommitA recorded snapshot of the lockfile update.
4Pull requestA review page showing exactly what would change.
5MergeThe approved change joins main; the temporary lane can go.

Why not edit main directly?

The branch-and-PR pattern creates a checkpoint. You can inspect the file list, line-by-line diff, automated checks, and explanation before the trusted branch changes. If the proposal is wrong, close it; main remains untouched. If it is right, merge it. This is GitHub’s reviewable safety rail.

A useful mental model: a branch is a draft lane, a commit is a saved checkpoint, a pull request is the review conversation, and a merge is the decision to place the reviewed change into the main project.

What “the diff” told us

The diff reported one changed file, with 60 additions and 34 deletions. Additions and deletions are line changes, not a count of newly added or erased programs. Most lines replaced old package metadata with new package metadata. A small diff made it easier to verify that no tutorial lesson or workflow was accidentally altered.

What happens next

The repair is merged, but the final operational proof is the next Supply-Chain Watch run. You chose not to trigger an immediate manual run, so the scheduled workflow will provide that confirmation.

If the next run is green

The five known findings are no longer blocking the audit. The repetitive failure emails caused by this incident should stop.

If it is red again

Open the newest run and read the first failed step. It may be a new advisory, an install problem, or an unrelated check—not necessarily the same incident.

If email continues

Compare the email’s workflow name and timestamp with the Actions page. A different workflow can send a similar-looking failure notification.

Honest status: all versions that caused run #425 were replaced with patched ones, and the fix is on main. Because no post-merge scan has run yet, “the next run passes” is the expected result—not a result already observed.

A five-minute checklist for any future GitHub failure email

  1. Confirm the repository name and workflow name in the email.
  2. Open the workflow run and find the first red step—not a later warning.
  3. Read the last 20–40 lines of that step’s log.
  4. Classify it: code/test failure, dependency advisory, configuration, permission, or service outage.
  5. Make the smallest safe change on a branch, open a PR, inspect the diff and checks, then merge only after review.

The second email: CI run #46

A different workflow, a different day, a different problem. After the security-scan repair merged, a routine CI run on main failed with three unrelated, pre-existing problems. The Security Scan check and the Lint check both passed — the red came from the test matrix, the coverage gate, and the unicode check.

24/33Test-matrix jobs failed — every Linux and macOS job; all 9 Windows jobs passed
<80%Code coverage sat below the required 80% threshold
21Emoji characters rejected by the unicode-safety check
The key insight: none of this was caused by PR #26. That PR touched only package-lock.json. These three failures were already sitting in the repository, invisible until CI ran against the new main.

The three failures, explained

Three checks, three different root causes. Each one is a small lesson about how computers and CI work.

1. “Permission denied” — the missing executable bit

A deployment script ran two helper scripts by calling them directly. On Linux and macOS, a file needs its executable bit set — a flag Git records — before the operating system will run it as a program. Both helpers had lost that flag, so every Linux/macOS job died with exit code 126 (“permission denied”). Windows ignores the executable bit, which is why all 9 Windows jobs passed and the failure looked platform-specific.

The fix: invoke the helpers explicitly through bash instead of relying on the flag — bash "$HOOKS_INSTALLER" rather than "$HOOKS_INSTALLER". That works no matter how the file mode was recorded. The POSIX test suite went from 11 of 13 passing to 13 of 13.

2. Coverage below 80% — untested code

Code coverage measures how much of the project’s code the automated tests actually exercise: lines run, branches taken, functions called. The repository requires at least 80% on all four measures. Four hook scripts had no tests at all, dragging the totals under the bar.

The fix: four new test files covering the previously untested hooks. Result — lines 88.5%, branches 80.1%, functions 95.4%, statements 88.5%. Every threshold passes.

3. Unicode safety — emoji in docs

The repository bans emoji in documentation and demo files (they can break tooling and render inconsistently), requiring plain text tags instead. Twenty-one violations were found across 8 files — warning, prohibition, check-mark, and cross-mark emoji used as status markers in guides, the demo showcase, an incident report, and one source file. Each was replaced with [WARNING], [BLOCK], [FAIL], or [PASS].

Why three failures at once: a CI run executes many independent checks in parallel. They fail independently too — fixing one does not fix the others, and a green Security Scan says nothing about the test matrix. Read each red check on its own terms.

The repair: pull request #27

Same playbook as #26: a fix branch, reviewable commits, automated checks, then merge after explicit approval.

1Branchfix/ci-health, created from main.
2Script fixHelpers invoked via bash; POSIX tests went 13/13.
3New testsFour test files for the untested hooks; coverage cleared 80% everywhere.
4Emoji sweep21 replacements across 8 files; the unicode check passes.
5MergePR #27 merged into main on September 13, 2026; the branch was deleted.

The near-miss worth knowing about

Five of the emoji replacements were initially applied to the wrong files because of a filename mix-up in the edit instructions. It was caught by comparing the actual PR branch against the verified local files before merging — not by trusting that “the instructions were followed.” The lesson: verify the artifact, not the process. Diff the branch; don’t just re-read the plan.

Honest status: the fixes are merged and each was verified locally (tests pass, coverage clears the bar, unicode check passes). The next full CI run on main is the final confirmation that all three checks are green in GitHub’s environment.

Plain-English glossary

Repository (repo)

The project’s home: files plus their version history.

Dependency

Reusable software the project relies on. A transitive dependency is installed by another dependency rather than named directly by your project.

Vulnerability advisory

A published record describing a known security weakness, affected version range, severity, and—when available—the patched version.

GitHub Actions workflow

An automation recipe stored with the repository. It can run on a schedule or in response to events such as a pull request.

Runner, job, and step

The runner is GitHub’s temporary computer. A workflow contains jobs; each job contains ordered steps. One failed step can make the job and workflow fail.

Lockfile

A record of exact dependency versions. It makes installations repeatable and is why changing package-lock.json changed what CI installs.

Exit code

A program’s compact result signal. Zero generally means success; nonzero means failure. The audit returned 1 after finding high-severity advisories.

CI

Continuous integration: automated checks that run against proposed or committed changes, such as linting, testing, or auditing.

Branch / commit / pull request / merge

A branch is a line of work; a commit is a saved checkpoint; a pull request proposes comparing and combining changes; merging accepts them into the target branch.

Test matrix

Running the same test suite across multiple combinations — here, three operating systems (Linux, macOS, Windows) times several Node.js versions. A failure on some combinations but not others points at a platform difference, like the executable bit.

Code coverage

The share of the project’s code that automated tests actually run. Reported for lines, branches (each path through an if/else), functions, and statements. This repository requires at least 80% on each.

Executable bit

A file flag, recorded by Git, that tells Linux and macOS “this file may be run as a program.” Without it, the OS refuses with “permission denied” (exit 126). Windows ignores it — which is why only some CI jobs failed.

POSIX

A family of operating-system standards covering Linux and macOS (but not Windows). “POSIX tests” means the checks that run on the Linux/macOS runners.
